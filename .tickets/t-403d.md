# Optimize start command: audit-friendly status bump

How: funnel through a shared status pipeline with optional start note/timestamp; Why: reduce duplicate logic and capture when work begins.

## Implementation plan
- Create a shared status transition helper that accepts `id`, target status, optional note text, and whether to append a timestamped note; reuse for `start`, `close`, `reopen`, and `status` commands.
- Extend `start` to optionally add a note/timestamp (flag `--note` or `--message`) recording when work began; ensure idempotent status updates (no duplicate writes if already in desired state).
- Centralize validation so invalid status transitions or missing tickets surface consistent errors; avoid multiple path resolutions.
- Add tests that start a ticket, confirm status and note append, and verify no double-write when status unchanged.
